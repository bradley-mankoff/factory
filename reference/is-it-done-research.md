No pi adaptation of Jevflow exists. Jevflow is a Claude Code Stop-hook plugin that runs phase checks and asks Jev whether the work is done, and the closest pi-native pieces use a separate reviewer agent rather than a classifier. The pi classifier API fits a cheap pre-review gate: one bool question over the spec plus a short diff costs a fraction of a cent and returns in under a second. The smallest proof of concept is a pi extension that runs Jev at the final settlement boundary and sends the agent back to work with a follow-up message when the answer is not done.

## 2. Jevflow and analogous projects on GitHub

Jevflow source: `https://github.com/Parth1811/JevFlow` (12 stars on 2026-10-24, language Python, MIT). It is the most-starred repo under the name "JevFlow" and matches the task description (phases with checks, Stop-time Jev verdict, live viewer). A backend-primitives repo named `Mawfyy/jevflow` (11 stars) shares the name but is a generic Jev workflow library, not the Claude Code plugin. The remaining `jevflow`/`JevFlow` forks and JEVATHON entries have 0 to 2 stars.

How Jevflow decides done: the agent writes a flow JSON with phases, each carrying a `done_when` definition and a shell `check`. Every time Claude Code tries to stop, the `Stop` hook (plus `SubagentStop`, `PreToolUse`, `PostToolUse`, declared in `hooks/hooks.json`) runs the checks for the current phase and sends the goal, the phase table, the check outputs, and recent transcript to Jev. Jev answers where the work stands (phase finished, stuck, off goal, claiming done too early). A fully tested policy in code then decides: keep going with a concrete next step, advance to the next phase, or allow the stop and archive the flow to `.jevflow/done/`. The standing rule is "Jev informs, code decides": a failing check always blocks even when Jev is confident, and Jev unavailability falls back to checks only.

Analogous projects, most-starred first:

* `davila7/claude-code-templates` (32,876 stars, `https://github.com/davila7/claude-code-templates`). A large Claude Code component catalog. Its `security/jev-vercel-sandbox` mod asks Jev whether one Bash command belongs in a Vercel Sandbox and with which profile. * `fitchmultz/pi-codex-goal` (195 stars, `https://github.com/fitchmultz/pi-codex-goal`). Codex-style goal tracking and continuation for pi. It keeps a goal alive across turns and resumes it rather than asking a model whether the work is done.

## 3. No pi extension checks "is it done" with a classifier

No npm package with keyword `pi-extension` or `pi-package`, no file in pi's `examples/` folder, and no GitHub pi extension found in this research uses a classifier or Jev call to check completion. The npm keyword search over both keywords (40 results each) surfaces goal, supervision, audit, and review extensions, but every completion check in them is either a chat-model reviewer or deterministic code. The only classifier call in pi's shipped examples is routing, not completion.

Closest matches and how each hooks in:

* `pi/examples/extensions/jev-router.ts` (ships with pi at `/opt/homebrew/lib/node_modules/@earendil-works/pi-coding-agent/examples/extensions/jev-router.ts`). The only example that calls `ctx.modelRegistry.classify()`. It registers a virtual model `jev/auto` and asks Jev one choice question ("How demanding is the software engineering work in `prompt`?", criteria `standard` versus `complex`, state truncated to 16,000 characters) to pick a planning model, then switches once to a cheaper model after the first successful edit. It hooks in at model routing (`pi.registerVirtualModel`, `route()`), never at completion.
* `pi-goal-x` (npm `pi-goal-x`, repo `tmonk/pi-goal-x`). Independent completion auditor as a separate agent run, plus a `goal_complete` style claim flow and an above-editor dashboard. It hooks in at goal lifecycle (goal commands, auditor run before archive), not at pi agent events, and the auditor is a chat model.
* `tintinweb/pi-supervisor` (npm `pi-supervisor`). Hooks in after each run and between tool calls at higher sensitivities, using a separate in-memory pi session as observer. The supervisor is a chat model chosen in `/supervise model`.
* `@schovest/pi-goal` (npm `@schovest/pi-goal`, ported from `@narumitw/pi-goal`). No model is involved, but it proves an extension can keep the agent working from `agent_end`.

## 4. Fit of pi's classifier API for an "is it done" check

Question types and criteria format: `models.classify()` (codemode) and `ctx.modelRegistry.classify()` (extensions) take `{ state, questions }` where `questions` maps an id to exactly one of three shapes, per `docs/codemode.md` ("Classify") and `docs/models.md` ("Use classifier models"). A `bool` question carries `instructions` plus `criteria: { true: meaning, false: meaning }` and answers with a `probability` of true. A `choice` question carries `instructions` plus `criteria: { label: meaning }` and answers with `choice`, per-label `probabilities`, and `confidence`. A `score` question carries `instructions` plus ordered `criteria: [...]` (lowest first) and answers with expected level `score` and `confidence`. One call can batch several questions against the same state. Question ids are for code and are not sent to the model, so each question must be self-contained: put the spec, the diff, and the meaning of each answer inside `state`, `instructions`, and `criteria`, and reference nested state with backticked paths such as ``ticket.messages[0].text``.

State size: Jev 1.14 and 1.13 accept 64k tokens per request (state plus all questions) and 32k per question (state plus any one question), at $42 per billion input tokens with free outputs, per `https://docs.typesafe.ai/models.md`. A `TypeSafe-Danger-Zone-Long-Context: true` header raises both limits to 262k tokens at the same per-token price, with lower speed and accuracy. The HTTP body cap is 32 MiB with at most 64 nesting levels. OpenAI's `gpt-6-luna` through the Decisions API is the exception: it rejects inputs above 922k tokens and gateway-times-out past about five seconds (roughly 600k input tokens), and it is the only classifier that also judges images. Direct `typesafe/jev-latest` needs `TYPESAFE_API_KEY`; the OpenRouter alias `~typesafe/jev-latest` uses `OPENROUTER_API_KEY`. Practical guidance from the shipped router is to truncate hard: `jev-router.ts` slices the prompt to 16,000 characters before classifying.

Latency and cost: the task's live data point stands: one bool question with a spec and a short diff used 370 tokens, cost about $0.000015, and returned in under one second on `openrouter/~typesafe/jev-latest`. That matches the catalog price ($0.000042 per thousand input tokens) and TypeSafe's System One design (fast structured judgment, no streamed text). Classifier usage is added to the `codemode` tool result and counts toward session cost; models without a catalog price (direct TypeSafe `jev-latest`) report tokens at no cost. Nothing in the docs contradicts using this call on every work-node finish: it is three orders of magnitude cheaper than the review agents it would gate.

Trigger events and keeping the agent working: the actionable boundaries are `turn_end` and `agent_before_settle`, per `docs/extensions.md`. Both handlers can append session-boundary entries (`custom`, `custom_message`, `context_edit`, `compaction`) and return `continue: true` for exactly one next model request. `agent_end` is notification-level for the low-level run (retries, compaction, queued work can still follow), but an extension can still send the agent back with `pi.sendUserMessage(text, { deliverAs: "followUp" })`, which is the documented `git-merge-and-resolve.ts` pattern. `agent_settled` is final and notification-only: use it when an integration needs to know pi will not continue on its own. `before_agent_start` can also reshape the prompt or tool set for the coming run, and `tool_call` can block an operation. For a completion gate, `agent_before_settle` is the natural trigger because it is the last point that can append a message and request one continuation in the same settling run; `agent_end` plus a follow-up message is the fallback that also works from Archon-spawned runs where the extension only observes.

Limits and gotchas:

* Classifier models never appear in `/model`. The extension resolves one with `ctx.modelRegistry.findOfType("classifier", provider, id)` (for example `("classifier", "typesafe", "jev-latest")`) and classifies without codemode. In codemode scripts the same call needs `"defaultTools": ["+codemode"]` in settings, which is off unless an MCP server turned it on.
* `classify()` never rejects on provider errors. It resolves with `stopReason: "stop" | "error" | "aborted"` plus `errorMessage`. The extension must check `stopReason` and define the error path (fail open to the review agents, or fail closed to one retry, never an infinite loop).
* `bool` answers carry `probability` but no `confidence`. `choice` and `score` carry both `probabilities` and a derived `confidence` (1 when all mass sits on one outcome, 0 on an even split). Threshold design differs per type, and TypeSafe's confidence guidance recommends three bands (act, proceed with caution, do not act) scaled to the stakes.
* An unconditional `continue: true` loops. Guard with a per-run attempt counter in extension state or a session entry, and cap retries (Jevflow caps at a bounded loop with a failure branch; `verify-gate-hook` caps at 4 blocks).
* Jev aliases move. `jev-latest` pointed at `jev-1.14.0` on 2026-10-24; tuned thresholds should pin a versioned id (`jev-1.14.0`) and re-tune on upgrade.
* Jev reads text only (string, object, or array of text). It takes no images through pi's classifier path; only `gpt-6-luna` judges images. Screenshots and rendered diffs must be converted to text first.
* English is the primary training language; other languages including CJK have lower accuracy, so threshold tests should use the Factory's own specs.
* Long-context mode is slower and less accurate than staying within default limits; prefer a short evidence pack (spec plus diff stat plus failing-check output) over the whole transcript.
* Switching models between turns drops the prompt cache. A gate that classifies from an extension does not switch the session model, so it costs no cache miss; a virtual-model gate like `jev-router.ts` accepts one miss per switch.

## 5. Proposal: smallest proof of concept that fits pi (not yet built)

This section is a proposal drawn from the facts above. Nothing in it is implemented.

Trigger: a pi extension loaded into the Archon work-node session listens on `agent_before_settle`, and only when the run's transcript shows the agent claiming the Bead's work is finished (for example its final message names the Bead id and says tests pass). Firing only on completion claims keeps the gate to one classifier call per node instead of one per turn.

State in: a small JSON object with three named fields: `spec` (the Bead description text, truncated to roughly 4,000 characters), `diff_stat` (the `git diff --stat` plus the unified diff truncated to roughly 8,000 characters), and `checks` (the exact command the node ran and its last 40 lines of output, following the `verify-gate-hook` convention of attaching failing output). Total state stays under about 4,000 tokens, far inside the 32k per-question limit, so no long-context header is needed.

Exact questions: one `bool` question with id `done`, instructions "Does the work described in `spec` hold against `diff_stat` and `checks`?", criteria true "Every requirement in the spec is implemented and every check passes" and false "Any requirement is missing, unproven, or contradicted by the diff or the checks". Optionally batch a second `choice` question with id `blocker` (criteria `missing_work`, `failing_checks`, `unclear_spec`, `none`) so the follow-up message can name the concrete next step without a second round trip.

Threshold: pin model `jev-1.14.0` through the `typesafe` provider (fall back to `openrouter` `~typesafe/jev-latest` when no TypeSafe key is present). Treat `probability >= 0.8` as done, `<= 0.4` as not done, and the band between as unsure. These numbers are starting values to calibrate against labeled Factory runs, not tuned constants.

On not done: return `{ entries: [{ type: "custom_message", customType: "is-it-done", content: <one paragraph naming the missing requirement plus the failing check output>, display: true }], continue: true }` from `agent_before_settle`, capped at two continuations per node by a counter kept in extension state. On unsure: do not continue; let the run settle and attach the Jev probability plus the `blocker` choice to the handoff so the expensive review agents (spec review, standards review) read the doubt. On classifier error (`stopReason` other than `"stop"`): fail open, let the run settle, and log the error with the node id so a missing key never blocks a Run.

## What is still unknown

* The exact `agent_before_settle` re-entry semantics inside Archon-spawned pi runs (whether a `continue: true` from an extension-loaded settings file reliably starts one more provider request under Archon 0.12.1) needs one live probe run, since the docs describe pi sessions and the spike report does not cover this event.
* The 0.8 and 0.4 thresholds are guesses. Calibration needs a labeled set of roughly 30 past Factory node transcripts (done versus prematurely stopped) scored against the proposed `done` question.
* Jev 1.14 accuracy on the Factory's spec style (Bead descriptions plus unified diffs) is unmeasured; the shipped `jev-router.ts` only validates Jev on task-complexity routing.
* Whether the Factory wants the gate to also run the shell checks itself (Jevflow style, checks outrank the model) or to trust the node's reported `checks` output is an open design call for Bead fac-60v.20.12.
