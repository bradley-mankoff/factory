# The Factory's pi folder

Every Factory Run uses this pi agent directory instead of the Human's personal `~/.pi/agent`, so AI nodes load only pi's built-in tools (`read`, `bash`, `edit`, `write`) and no personal extensions or skills, and their sessions stay apart from the personal ones. Project Managers do not use it: they start the Human's own pi, so their sessions are kept with his other pi sessions (the Human, 2026-11-07). The evidence is in `reference/archon-pi-spike/RESULTS.md` (round two, item B4b; round three).

This folder holds the files without secrets. The live directory is `~/.local/share/factory/pi-agent/`, outside this repo, because its `auth.json` gives access to the model providers. (`~/.factory/` is not used: it belongs to the earlier Factory and to Factory.ai's skills.)

## Files

- `settings.json`: the pi packages every Run loads, each installed with `pi install` from its own repo (fac-qpv.8.1): pi-claude-bridge 0.9.3, which install.sh installs into this folder's own `npm/` so the Factory borrows nothing from the Human's personal pi but the login (the Human, 2026-10-21), so a Chain can reach Claude (2026-10-19), and the pi-chains and pi-flows packages. The bridge adds the `claude-bridge/` provider and no tools, so nodes on other Chain entries are unchanged. Project Managers do not use this folder; the Human's own pi settings load pi-claude-bridge as a package. `defaultThinkingLevel: "high"` covers any node without `effort`. `hideThinkingBlock: true` hides thinking in Runs' sessions; a Project Manager's thinking is hidden by the Human's own settings (the Human, 2026-10-23).
- `trust.json`: trusts the folder where Archon puts every Run's worktree, so a project's own `.pi/` extensions load in Runs. pi applies the closest saved decision of a folder or its parents.
- `chains.json`: a link that install.sh makes to the Chains file the Mac's Profile names, `~/.config/factory/chains.json` by default (`fac-qpv.6.3`). The pi-chains package reads it from this folder, so every session here registers one selectable model per role under `chain/`, each running on its Chain at that entry's thinking level (`fac-qpv.1.1`). A Chain entry names one model on one account, `provider/model`, or one model on a group of seats (`GLOSSARY.md`), which is how a GPT entry reaches either ChatGPT login. A request goes to the first entry whose account has usage left and stays on the seat that answered last while its account has usage, for the prompt cache. When its seat runs out the session moves to the same model on the other seat, and only when every seat is used up does it move down the Chain (`fac-qpv.1.3`). When a provider's final error says the account has run out, the package marks that account in `${XDG_STATE_HOME:-~/.local/state}/pi-chains/accounts.json`, with the reset time the message names or one hour when it names none, and asks pi for one more request, which goes to the next seat or the next entry; every agent on the Mac reads the same file, so they all skip the account until its mark expires (`fac-qpv.1.2`). Every session in this folder loads it, so an AI node can name a Chain model in its `model:`. install.sh also installs it into `~/.pi/agent/`, so a Project Manager, which runs the Human's own pi, starts on its Chain (`fac-qpv.1.4`). Archon 0.12.1 loads this folder's packages, binds them before it looks the model up again, and calls `session.setModel()` with what the package registered (`packages/providers/src/community/pi/provider.ts`, LOOKUP-2 around line 1265). A live two-node Run on 2026-11-07 in a scratch repo proved it: both nodes named `model: chain/work`, and each node's session recorded `chain/work` as the selection and `opencode-go/deepseek-v4.1-flash` at `max` as the model that answered (Run `5a8ab095-bb2e-439c-9156-02c973b457ca`, recorded in Epic `fac-qpv.1`).
- The pi-flows package, which install.sh installs here from its own repo, runs the checks a node's Workflow assigns when the agent tries to finish (`fac-qpv.3.1`). A Workflow keeps one file per node in a `flows/` folder beside its YAML, one check per line; the prompt that `bin/node-prompts` writes for a checked node carries a `FLOWS` marker naming the node, folders and the project's check command, and the package reads it from the handler's context. A Workflow is the one place a node's checks live: a Bead whose definition of done differs is built by a forked Workflow with that node's `flows/` file, never by a list of its own. A failing check sends the agent back with the check's message, at most twice; after that the agent finishes and the failures go to the Run's artifacts as `flows-failed.txt`, where `bin/work-finished` reads them for a build. A session with no marker is left alone, which is why review nodes can run without checks. The checks are short scripts in the package's own `checks/` folder, beside its `extensions/`, which is where it finds them (fac-qpv.8.1).
- `claude-bridge.json`: settings for pi-claude-bridge, copied from the Human's personal file: a Pro plan, no paid long context. With no `plan` set, the bridge prints a notice at start-up. The bridge reads this file from `PI_CODING_AGENT_DIR`, so it must be here and not only in `~/.pi/agent`. Claude signs in through the Human's Claude Code login, not `auth.json`.
- No `models.json`. pi 1.3's built-in catalog lists every model the Chains name, such as `opencode-go/deepseek-v4.1-flash` and `opencode-go/muse-spark-1.3-contributor`, and pi-claude-bridge adds the `claude-bridge/` models. FactoryClaw runs on OpenClaw rather than pi, on Muse Spark at high (`fac-qpv.1.4`). The personal `models.json` adds only stale entries, and it holds the OpenCode key as plain text.

## Setting up the live directory

`scripts/install.sh` sets it up: it installs pi-claude-bridge and the pi-chains and pi-flows packages with `pi install` into this folder, and merges `settings.json`, `trust.json` and `claude-bridge.json` into `~/.local/share/factory/pi-agent/` (merged, so the settings pi adds and the projects that setup trusts are kept), links `chains.json` to the Profile's Chains file there and links `auth.json` there.

`auth.json` is a symlink to the personal one, not a copy. xAI signs in by OAuth, and a copy would hold a second refresh token: a refresh in one directory can make the other's token stale, so the Human would sign in twice as often. With the symlink, one `/login` in the Human's own session serves both. pi writes `auth.json` with `writeFileSync`, which follows the symlink. It also offers the Factory the Human's other providers; nodes name their model explicitly, so nothing uses them unasked.

Check it with a read-only probe that prints provider names and credential types, never token material:

```bash
python3 -c 'import json,os; d=json.load(open(os.path.expanduser("~/.local/share/factory/pi-agent/auth.json"))); print({k: v.get("type") for k, v in d.items()})'
```

An expired login is renewed by the Human in their own pi session (`/login <provider>`); nothing in the Factory logs in.

## Pointing Runs at it

Archon reads `PI_CODING_AGENT_DIR` once, when `archon` starts. Each Factory project sets it in its own `.archon/.env`, which Archon loads at start-up and which is never committed:

`scripts/install.sh <repo>` writes it there, with the project's other values, and adds `.archon/.env` to the project's `.gitignore`.

Then a plain `archon workflow run` in that project uses the clean setup, and the Project Manager's own pi session is not affected. On 2026-10-17 a one-node Run started this way in a scratch repo, with `PI_CODING_AGENT_DIR` unset in the shell, had exactly the tools `bash`, `edit`, `read` and `write`, no skills, and thinking `low`, and its session was written under `~/.local/share/factory/pi-agent/sessions/`.

## Marker-driven packages

pi-flows is the one package that acts per node. It follows the tested pattern in `reference/archon-pi-spike/extensions/guard.ts`: use the handler's `ctx`, never `pi.*` inside a handler, and find the node from a marker in its prompt, so a node without the marker is left alone. Add another only when a named Workflow needs it.
