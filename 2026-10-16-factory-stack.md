# The Factory (spec, 2026-10-16)

Status: agreed with the Human on 2026-10-16. This is a greenfield build in this repo, `~/Developer/personal_code/factory/`. It takes no code from the earlier Factory in `~/Developer/graph_engineering`, needs no migration from it, and keeps no compatibility with it.

## Goal

The Human gives an Idea in a few plain sentences. The Factory turns it into reviewed, merged code in the right project repo. Along the way it asks the Human only what the Human alone can answer: what the Idea means, and whether the result looks and feels right.

The judgment lives in models, not in code. A Project Manager leads each project: it plans, decides and checks results. Beads, Archon, git, GitHub, herdr and pi are its tools. The Factory writes code only for what a model cannot do reliably, so when models improve, the Factory improves without code changes. There is no poller and no dispatcher program. The earlier Factory, and an earlier attempt before it, each grew around a polling program that held the work's judgment as code, and each became hard to manage.

**Versions** (the Human, 2026-10-21). The MVP is v0: real tasks run through real projects end to end, from old or new Ideas and Beads. It was reached on 2026-10-18, when Runs built and merged Beads of socratic-dialogue-facilitator (pull requests 9 to 17) and of both toy repos (Epic `fac-60v`, closed). Each iteration after it is the next tenth, v0.1, v0.2 and so on toward v1, each an Epic in this repo's Beads. v1 (the Human, 2026-10-22) is the MVP enriched with a set of additions that are high in value and not hard to integrate, built largely on others' work and proven valuable in the Human's own use: robust memory scoped to each kind of agent; Jev governance asking "is it done" and "is it safe"; perhaps one to three more Jev uses; and codemode, chiefly for the Scout. The Beads in v1 carry the label `v1`.

**Size target.** The whole Factory stays under 5,000 lines. That counts Factory-specific code, skills, docs and AGENTS.md files, not their comments, docstrings or blank lines (the Human, 2026-11-09). It does not count memory, the copied evidence in `reference/`, or the tests in `tests/` (the Human, 2026-11-08). Whether something counts is judgment: does the Factory depend on it, or merely use it (the Human, 2026-11-09)? Conveniences do not count: the menu bar apps, the herdr plugins, micro, the markdown preview viewer, and the terminal click and paste conveniences. What counts is this repo's own code, skills, docs and AGENTS.md files, never those files as they live inside each project folder; core pi, core Archon and core Beads are used, not maintained, and never count. No file stores the count; scripts/size (named in `AGENTS.md`) gives it. Nothing enforces it.

## Words

- **Human**: the person who owns every project and decides what matters.
- **FactoryClaw**: the OpenClaw agent that carries messages between the Human and the Project Managers.
- **Project Manager**: the agent that leads one project.
- **Idea**: a few plain sentences from the Human about what a project should do.
- **Spec**: the written, domain-modelled version of an Idea, in the project's own words. A Spec is stored as the description of an Epic, not as a file in the project repo, so specs do not pile up as documents.
- **Epic**: a parent Bead holding one Spec and the Beads made from it.
- **Bead**: one unit of work in Beads, shaped like a ticket in Matt Pocock's `to-tickets` skill. A Bead is a thin vertical slice that can be shown working on its own. It is sized to fit one fresh context window, and it names the Beads that block it. The `to-beads` instructions set a minimum size as well as a maximum, so every Bead is worth a Workflow of its own.
- **Human gate**: a node in a Workflow that waits for the Human's answer.
- **Agent**: a model session with its own instructions, tools and lifetime. FactoryClaw, PersonalClaw, each Project Manager and the session that each AI node of a Run runs are all agents (the Human, 2026-10-19). The agent in an AI node is named by its kind: the work agent, the spec review agent, the standards review agent, the demo agent, the research agent.
- **Scout**: an agent a Project Manager starts to look up one question, which hands back a short answer and a file. Scouts are not part of Workflows.
- **Workflow**: an Archon workflow file. It says how one piece of work gets done: which nodes run, in what order, on which model, with which tools.
- **Run**: one execution of a Workflow.
- **Node**: one step in a Workflow. An AI node runs an agent in pi; a shell node runs a command.
- **Decision**: a question only the Human can answer.

Words this Factory does not use, because they belonged to the earlier one: Boss, Dispatcher, Ticket, Step, Worker (say work agent), Helper, Reviewer (say spec review agent or standards review agent), Portfolio Manager, lights-on, lights-off.

## The stack

### 1. FactoryClaw (outermost layer)

- **How the Human reaches it**: Telegram, or directly in its terminal interface.
- **Job**: carry messages between the Human and the Project Managers. It relays Ideas to the right Project Manager, relays Decisions to the Human, and sends the Human's answers back.
- **Routing**: FactoryClaw's `AGENTS.md` sends each kind of request to one skill. The skills call `bd`, `herdr` and `archon` directly. There is no `factory` command in between. If FactoryClaw turns out too slow, or does not keep to its guardrails when it calls the tools itself, a thin command is the fallback. The earlier Factory's command is kept at the git tag `archive/factory-command-2026-10-16` in `~/Developer/graph_engineering`, as an example to read, not to reuse.
- **Opens and closes Project Manager panes**, with herdr commands from a skill, and nothing else does. Every Project Manager pane is in the herdr session `factory`, one workspace per project; the Human watches them with `herdr session attach factory`. The session's server runs as its own launchd job, `factory.herdr`, started at login and set up by `scripts/install.sh`; FactoryClaw only starts that job when the server is down. Started by FactoryClaw's own exec, the server ran inside OpenClaw's process group, its panes inherited OpenClaw's `OPENCLAW_SHELL` marker, and OpenClaw refused every Project Manager's `openclaw agent` message ("would lose inter-session attribution"). (The earlier Factory's session of that name was stopped and deleted on 2026-10-17; the Human had no use for it.) A pane opens when a project starts and normally stays open until the project is finished; convenience matters more than the memory an open pane uses. The Human can ask FactoryClaw which projects are open and ask it to close some. When the Human asks for work on a project whose pane is closed, FactoryClaw opens the pane first. **FactoryClaw owns each Project Manager's start-up and shut-down** (the Human, 2026-10-19): "get to work on <project>" starts the Project Manager, giving it `FactoryClaw: The Human asks you to get to work.` as pi's first message when it opens the pane and typing that message into a pane that is already open, and "stop <project>" closes the pane. From there the Project Manager chooses its own work, building ready Beads and running independent ones in parallel, without asking FactoryClaw or the Human. A pane opened with no first message reviews its claimed Beads, its ended Runs and its ready Beads, then proposes the next steps and waits for the Human to accept; FactoryClaw's "get to work" message still means act rather than propose (`fac-qpv.2.2`). No program reopens a pane the Human closed: there is no launchd job, no keeper and no project list that forces panes open.
- **A reopened pane starts a fresh session.** Nothing is lost, because the state lives in Beads, git and the Project Manager's memory. There is no need for one long session that compacts over and over.
- **Skills**: one skill per job: relay an Idea, start or stop a Project Manager and list the running ones, relay a Decision and its answer, report a project's state. Its context stays narrow so it answers fast.
- **Messages to the Human**: only what the Human needs. That means grilling an Idea, Decisions, Human gates, and starting or stopping the Factory. FactoryClaw sends no acknowledgements, "started" notices or "done" reports. One exception is forced by OpenClaw: it must reply to every message the Human sends on Telegram (a silent `NO_REPLY` does not waive a direct chat's reply), so when the Human needs nothing back, the reply is one line naming where the message went.
- **Memory**: how the Human likes to be spoken to; how the Factory works, and what about it is being changed now; the basics of each project, past and present.
- **Where its files live**: FactoryClaw is an existing OpenClaw agent with its workspace at `~/.openclaw/workspace-factoryclaw/`. This repo holds the source of its `AGENTS.md` routing, its skills and short `BOOT.md` and `HEARTBEAT.md` files, and, where the Mac's Profile names FactoryClaw as the outer layer (`fac-qpv.6.3`), `scripts/install.sh` puts them into that workspace, replacing what is there. Project setup writes the list of Factory projects, with each repo's path and pane name, into the workspace's `TOOLS.md`, which OpenClaw loads into every FactoryClaw session and which FactoryClaw rereads before choosing a project: on 2026-10-18 a copy read earlier in the same chat sent the calculator Idea to a scratch project that was no longer listed. The install also sets FactoryClaw's exec allowlist to the four commands its `AGENTS.md` names (`herdr` and `bd` as bare names, because the allowlist matches the resolved binary and Homebrew's links resolve into versioned folders; and `archon` by the real path of the wrapper install keeps under `~/.local/share/factory/commands/`, because FactoryClaw calls the `~/.local/bin/archon` link and OpenClaw matches what that link resolves to), because OpenClaw holds for the Human's approval any command outside the list and any command with an unquoted glob.
- **Learned skills become Factory Beads** (fac-60v.23, 2026-10-19). OpenClaw's Skill Workshop, on by default for every agent, saves a learned skill after hard multi-step work. For FactoryClaw such a skill copies steps from the skills the Factory installs and goes stale (on 2026-10-19 the learned `factory-herdr-relay` still waited for a model name the panes skill had dropped, and FactoryClaw followed it instead of the skill), but its save marks a place where those skills fell short. The Factory's OpenClaw plugin `openclaw-plugins/workshop-catch/` listens on the `skill_changed` hook: for a Workshop save under FactoryClaw's agent folder, it reads the new `SKILL.md`, archives the skill with `openclaw skills workshop archive --agent factoryclaw` (not awaited inside the hook, which runs while the Workshop holds the skill's lock), and files a Bead under the Factory's Epic holding the skill and asking whether FactoryClaw needs a new or changed skill. Other agents' learned skills are left alone. Its `message_sending` hook drops FactoryClaw's "💾 Learned … Say undo" notice, which the Human does not need and whose undo no longer applies. The hook carries no agent id for a Workshop save, so the plugin tells FactoryClaw's skills by their folder (`~/.openclaw/agents/factoryclaw/`); the gateway runs with a bare PATH, so `scripts/install.sh` gives the plugin its own. Restoring an archived skill counts as a new save and is caught again; that was the test (restored `factory-herdr-relay` was archived 1.7 seconds later and filed as fac-60v.25, with no message to the Human).

### 2. Project Managers (one per project)

- **Where it lives**: one terminal pane per project, in herdr, running the Human's own pi inside the project's repo. The Human can type into the pane directly; FactoryClaw types into it with `herdr agent prompt`.
- **Model**: a Chain, `chain/pm`, which `project-manager/start` reads from the Profile's `PM_MODEL` (fac-qpv.1, fac-qpv.6.3). On the personal Mac it is Claude Opus 5.5 at medium, then Muse Spark 1.3 contributor at maximum. The Chain sets the thinking level, and when Claude's plan runs out the Project Manager carries on on the next model instead of stopping until it resets. Each Mac's Chains are in the file its Profile names, `~/.config/factory/chains.json` by default.
- **Models elsewhere** (fac-qpv.1, the Human, 2026-11-06). Every role runs on a Chain: the ordered list of models, each with its thinking level, that the pi-chains package walks when an account runs out. On the personal Mac, the Project Manager and the spec review run on Claude Opus 5.5 at medium, then Muse Spark 1.3 contributor at maximum; the work agent, the standards review, the research and demo agents, Archon's default and the Scout run on DeepSeek v4.1 Flash at maximum, with no fallback. FactoryClaw runs on OpenClaw rather than pi, so it keeps `opencode-go/muse-spark-1.3-contributor` at `high`, a middle level that keeps it quick. The Chains are in the file each Mac's Profile names (`~/.config/factory/chains.json` by default), one file per Mac, and install links each pi folder's `chains.json` to it (fac-qpv.8.1). Archon's small, medium and large tiers and its @aliases, `project-manager/start` and the Scout's agent definition name the Chain roles (`chain/pm`, `chain/spec-review`, `chain/work`, `chain/scout`), never a model or a seat, and the Workflows in the library name the same roles. Muse Spark and DeepSeek always run at maximum, and DeepSeek never serves as Project Manager or spec review. Choosing a model directly, with `/model` in a session or in a Run's node, is the one case a Chain does not cover, so pi's own `modelThinkingLevels` setting in `settings.json` gives each model its level: Opus 5.5 at `high`, DeepSeek v4.1 Flash at `max`, Muse Spark 1.3 contributor at `xhigh` (its maximum; pi clamps `max` down to it). The Factory's copy is `pi-agent/settings.json`, which install merges into a Run's pi folder, and the Human's own pi folder carries the same block by hand. Muse Spark costs $0.10 and $0.20 per million input and output tokens on OpenCode Go at all hours.
- **Claude usage** (the Human, 2026-10-25; the Chains since fac-qpv.1, and no check since fac-vse). The Claude plan has two windows, 5 hours and a week, and no monthly limit. No helper reads the plan's usage: when an account runs out, the Project Manager and its reviews move to the next model in their Chain, and only a Chain whose every account is used up stops, naming each account and its reset time. FactoryClaw does not check usage or choose a model: it runs on the model and thinking level its Profile names, and the model-roles skill holds the Human's model preferences.
- **Job**:
  - turn an Idea into a Spec (grilling with the Factory's grilling skill, adapted from Matt Pocock's `grilling` and `grill-with-docs`, with domain modelling so the project's words stay tight and shared; or with the Factory's `wayfinder` when the Idea is bigger than one Spec; then the `to-spec` skill, adapted to write the Spec into a new Epic);
  - split the Spec into Beads under its Epic (a `to-beads` skill, adapted from `to-tickets` to use Beads words and `bd` commands);
  - keep the dependencies between Beads right;
  - for each Bead, choose a core Workflow from the Workflow library, or one of the person's own from their group, or write a new one in that group, check it, and start a Run;
  - read each Run's result and decide what happens next.
- **Research Workflows.** A Project Manager also writes Workflows to gather information: how an Idea fits the code, which files and excerpts a planned Workflow needs, what a library does. Research nodes write their findings to a file that opens with a short answer, then hand back the file's path. The Project Manager reads the full file only when it decides it needs to. This keeps its own context clean.
- **Notices** (`fac-qpv.2`). A Run's last node writes its ending as one dated line to the Project Manager's Notice file, `~/.local/share/factory/notices/<pane>.md`: `bin/finish` reads the notes the Run leaves in its artifacts, composes the line and appends it with `bin/tell-pm`, and nothing types into any pane, so a half-typed draft in the Project Manager's editor is never touched. The line takes the pane from the first field of the Run's message, `"<pane> · <bead id>"`, which the Project Manager writes when it starts the Run and `bin/finish` passes to `bin/tell-pm`, so the pane name first is the whole address of a Notice (`fac-qpv.9`). The `pi-notices` package, installed in the Human's pi, watches the file `PI_NOTICES_FILE` names, which `project-manager/start` exports as that path, and delivers each new line with `pi.sendMessage` as a visible message, `triggerTurn: true` and `deliverAs: "followUp"`: an idle Project Manager starts a turn on the Notice, and a busy one gets it when its turn ends. It delivers only lines written after its session started, because a Run that ended while no session was open is found by the Project Manager's start review (`fac-qpv.2.2`), and replaying the file as well would have the Project Manager record that Run twice. A Notice names the Run, the Workflow, the Bead and how it ended, so the Project Manager records it and takes up the next ready Bead without waiting for the Human. A session that starts instead gets a proposal: `project-manager/start` passes pi an opening message asking for the start review — claimed Beads, ended Runs, ready Beads — whose next steps wait for the Human to accept, and a first message given on the command line replaces it (`fac-qpv.2.2`).
- **Judgment about oversight.** The Project Manager decides when a Run's result needs its own reading, and when the checks built into the Workflow are enough.
- **Memory**: its tools and how each has worked here before; the project's history; the project's long-term goals.
- **Definition**: written in this repo and installed for every project. `project-manager/instructions.md` holds its instructions; `project-manager/start` starts the Human's own pi in the repo's top folder, appending those instructions and `GLOSSARY.md` to its system prompt. With no first message it also gives pi one asking for the start routine, which reviews what is waiting and proposes the next steps for the Human to accept; a first message given on the command line replaces it, so FactoryClaw's "get to work" still means act (`fac-qpv.2.2`). It is his pi setup, not a separate one (the Human, 2026-11-07): it leaves `PI_CODING_AGENT_DIR` unset, so pi reads `~/.pi/agent`, and passes no `-ne` or `-ns`, so his extensions, skills and packages load as in his other sessions, and the Project Manager's session is kept with his other pi sessions. His settings already load `pi-claude-bridge`, which gives the `claude-bridge/` models, and his paste and stash. Anything a Project Manager needs that his setup does not load yet, `scripts/install.sh` installs as a pi package from its own repo (fac-qpv.8.1): `pi-beads`, which adds the project's `bd prime` output to the first prompt (the Human, 2026-10-22) and saves the session's lasting lessons with `bd remember` when it ends or compacts (`fac-60v.20.19`); `pi-links`, which turns each real Bead id in a reply into a link to that Bead on the board, naming the reply's project (`fac-qpv.7.1`); `pi-notices`, which delivers each new line of the Project Manager's Notice file into its conversation as a message of its own (`fac-qpv.2.1`); and `pi-chains`, which makes the role models under `chain/` selectable, so the Project Manager runs on `chain/pm` (`fac-qpv.1.4`). pi's sample `subagent` stays a link install makes. The Factory's four planning skills and `record-demo` come from `~/.agents/skills`, where the install links them in place of his copies of the same names; Matt Pocock's `domain-modeling`, `tdd`, `codebase-design` and `prototype`, which those skills use, and the `archon` skill are already there in his setup. The launcher reads its model, the Workflow library and the workspace shape from the Profile, `~/.config/factory/profile` (`fac-qpv.6.3`), exporting the library as `LIBRARY` and the shape as `WORKSPACE`, and turns off pi's update notice with `PI_SKIP_VERSION_CHECK=1`, and it exports the two settings the packages read here: `PI_NOTICES_FILE`, the pane's Notice file, and `BEADS_BOARD_PORT`, the Profile's `BOARD_PORT`. In a herdr pane it renames the pane `pm-<folder>` and exports that name as `FACTORY_PM_AGENT`, so a Run started there names its Project Manager; `bin/pm-pane` holds the one rule for that name, which the launcher and project setup both call, so the rename and the name in `.archon/.env` cannot drift; under the worktree shape the pane is named after the worktree, and `start` first calls `bin/archon-register` for the worktree it was run in: that helper finds the repo's main checkout and, when Archon has not registered it, runs the core Workflow `factory-register` there, with no model and no worktree, so a Run started in a worktree has the project Archon can find it by (`fac-qpv.6.5`). The registration's failure is reported and does not stop the Project Manager, whose planning needs no Archon. `project-manager/pm` is the shorthand that starts this launcher in the folder it is run in.

### 3. Tools of the Project Manager

- **Beads (`bd`)**: the record of what work exists, what blocks what, and what is done. One Beads database per project repo.
- **Archon**: runs Workflows. Each Run gets its own git worktree and branch. A Project Manager starts a Run with `archon workflow run`, follows it with `archon workflow status`, `logs` and `wait`, finds paused Runs with `archon workflow attention --json`, and answers a pause with `archon workflow approve`, `reject` or `answer`. It also owns cleanup: once it no longer needs a Run's worktree it removes it with `archon complete <branch>`, because nothing else does. A Run is kept as its Workflow at the commit it ran from and its logs, never as a whole worktree (the Human, 2026-10-19): a worktree that Archon keeps for uncommitted or unpushed work gets the Project Manager's look, then `--force` (`archon isolation cleanup` acts on every project at once and refuses worktrees made by older Archon versions). On 2026-10-18 about 300 leftover worktrees held 288 GB.
- **git and GitHub**: branches, commits, pushes, pull requests and merges, used heavily. GitHub checks on pull requests can replace local gate code.
- **herdr**: gives each Project Manager pane an address. It is the channel from FactoryClaw to a Project Manager. A Run no longer types into its Project Manager's pane: its last node writes a Notice instead (`fac-qpv.2.1`).
- **pi**: the harness for Project Managers and for every AI node.

Not used: herdsman. Archon runs nodes in parallel, and nothing else needs child panes.

## Layout of this repo

- `GLOSSARY.md`: the words above, kept as the one glossary. The name follows Matt Pocock's skills, which renamed `CONTEXT.md` to `GLOSSARY.md` on 2026-08-15.
- `AGENTS.md`: rules for agents working on this repo.
- `skills/`: `to-spec`, `to-beads`, the grilling skill and `wayfinder`, the one planning chain from Idea to Beads for Project Managers and for the Human's own pi sessions alike (the Human, 2026-10-18), plus `record-demo` for Runs and for a Project Manager that records a demo after a failed one. They are written for any agent; their steps through FactoryClaw apply only to a Project Manager. `scripts/install.sh` links the four planning skills and `record-demo` into `~/.agents/skills`, the four in place of Matt Pocock's skills of the same names, whose `to-tickets` and issue-tracker setup published plans to GitHub issues or `.scratch/` files instead of Beads. A later `npx skills add mattpocock/skills` would bring his copies back; the install then skips each one and names the command that removes it.
- `project-manager/`: the Project Manager's definition.
- `factoryclaw/`: the source of FactoryClaw's `AGENTS.md` routing and its skills, in `factoryclaw/skills/`.
- `openclaw-plugins/`: the `workshop-catch` OpenClaw plugin, installed to `~/.local/share/factory/openclaw-plugins/` and linked into OpenClaw.
- `prompts/`: the conventions for each kind of AI node in a Workflow (`work`, `task`, `review_spec`, `review_standards`), adapted once from Matt Pocock's tdd and code-review skills and owned here since (the Human, 2026-10-19). The fuller module and test design guidance sits in `prompts/guides/`: `module-design.md` and `test-design.md`, each named by a prompt only when the change's condition calls for it, so every rule that must not be missed stays in the short prompt (fac-6a7.2). `bin/node-prompts` reads them into a Run as JSON, and each AI node's prompt starts with its kind's convention. The work and task conventions have the agent end its final message with a closing account of each acceptance criterion, one line per criterion marked met with its evidence or unmet with what is missing, and the `closing-account` check reads that account. Archon's command files were passed over because they cannot see `$LOOP_PREV`, which carries review findings back to the work. Matt's two-axis code review is split into a spec review and a standards review, run as separate nodes, so a pass on one cannot hide a failure on the other.
- `bin/`: `node-prompts`, `bead`, `work-finished`, `finish`, `pm-pane`, `archon-roles`, `archon-register`, `tell-pm`, `land` and `board`, installed to `~/.local/share/factory/bin/`. `archon-register` registers a repo with Archon from its main checkout when a Project Manager starts in one of its worktrees (`fac-qpv.6.5`).
- `bin/land`: how a Run lands its commits, in one place, so the build Workflows call it instead of writing the pull request and merge nodes themselves (`fac-qpv.6.4`). The Mac's Profile chooses: under `pull-request` it pushes the Run's branch, opens a pull request into the base branch and squash-merges it, as the personal Mac lands; under `squash` it squashes the Run's commits onto the base branch in a worktree of its own, runs the project's check on that tree and pushes the base branch, as the work Mac lands, opening no pull request at all. It lands on `$BASE_BRANCH`, Archon's value, or `--base`, and `--hold` stops it before the base branch moves, for a Workflow that puts a Human gate between preparing the landing and making it. Before any git command that moves a branch it refuses a target the Profile protects for that repo, and under the squash landing also every target of a repo the Profile does not name, saying which setting refused it; the repo is the folder of the repo's main checkout, which is the name the Profile uses. It leaves how the landing ended in `$ARTIFACTS_DIR/landing` and what a gate holds in `$ARTIFACTS_DIR/held`, one line each, for `bin/finish` to read, because Archon refuses to splice a failed node's output into a later node.
- `bin/board` and the launchd job `factory.bdui`: the Beads board, beads-ui, on this Mac (`fac-qpv.7.3`). A Bead id in a Project Manager's reply is a link to that Bead on the board, so the board has to be running after a reboot and has to know the link's project: `bin/board` starts the board on the port the Profile names (`BOARD_PORT`, 3917 without one), the port those links name too, and registers every project in `~/.config/factory/projects` with it, since beads-ui keeps the projects it knows in the running server and not on disk. Its own start runs in the first project in that list with a Beads database, because a fresh browser tab shows the board's current project and the home folder holds none; the home folder is the fallback only when no project has one. `scripts/install.sh` writes `~/Library/LaunchAgents/factory.bdui.plist`, which runs `bin/board` at login with a PATH holding bdui's folder, and runs the script itself so the board is up the same day; loading the job would start a second server that races for the port, so install runs the script first. A board registered twice knows the project once.

## How work flows

1. The Human sends an Idea to FactoryClaw. FactoryClaw picks the project, or asks the Human which one, and types the Idea into that project's Project Manager pane, opening the pane first if it is closed.
2. The Project Manager grills (through FactoryClaw, or directly when the Human is at the pane) until the Idea is clear, then writes the Spec as a new Epic and presents it to the Human for review. Away from the pane, FactoryClaw reads the Epic and summarises the Spec for the Human. The Human approves it or asks for changes.
3. The Project Manager writes the Epic's Beads with `to-beads`, with blocking edges between them.
4. For each Bead whose blockers are done, the Project Manager picks or writes a Workflow, runs `archon workflow test` on it, and starts a Run.
5. The Run does the work in its own worktree, checks it, reviews it, and lands it as its nodes and the Mac's Profile say: a pull request into the base branch and its squash merge, or the commits squashed onto the base branch, checked again and pushed (`bin/land`). Its last node writes its Notice with `bin/finish`, which composes one dated line from the notes in the Run's artifacts and appends it with `bin/tell-pm`: it names the Run, the Workflow, the Bead and how it ended, and the pi-notices package delivers it into the Project Manager's conversation as a message of its own (`fac-qpv.2.1`).
6. The Project Manager reads the result, writes a comment on the Bead (Run id, Workflow file, outcome, one line on what went wrong if anything), closes the Bead or plans a follow-up, and moves to the next ready Bead.

### Review and landing

A Workflow carries enough review that reaching its landing node means the work may land. The landing node lands, through `bin/land`; landings do not wait for the Human otherwise. Two kinds of review node:

- **Human gate for taste and fit.** The Run pauses and the question reaches the Human through FactoryClaw: does this look and feel right, and does it fit the Idea? The Run records a demo video of the change working, and FactoryClaw attaches it in the chat. The Human watches each project being built piece by piece, so the video shows the new piece. Errors are never a taste question: they are defects in every project, which the Run's review and its demo script catch, so no video showing an error reaches the Human. The Human judges from the video alone: approving it approves the landing, so the message carries no address of the change, and the video is not added to the change (Human, 2026-10-18). Whether a Workflow has this node, and where, is the Project Manager's call for that Bead, but the node is only for what a person judges by looking at it: a screen, a page, or text a person reads. Data, numbers, schemas, file formats and pipelines get no gate, since their rightness is for the checks and reviews (the Human, 2026-11-11, fac-bes).
- **Code review.** One ordered pass of two adversarial reviews, each in a fresh session separate from the node that did the work, and no loop: no review sends the work back, so a Run cannot repeat it. The spec review runs first and only reads: does the change do what its Bead asked, no less and no more? When it withholds approval the Run ends, its findings go on the Bead, and the Project Manager decides, because a wrong or missing requirement needs its judgment. When it approves, the standards review reads the diff for the repo's documented standards and its code smells, fixes what it finds inside the files the diff touches, and commits the fixes as one commit of its own, so a small standards issue never costs another Run. The checks run again after it, then the Run lands, or in the gated build holds the landing, records its demo and waits at the Human gate first, so the Human judges the version that will land. The standards review withholds approval only for a defect it cannot fix inside those files, and says why.

The Human answers on Telegram: on the phone when away from the computer, and on the desktop otherwise. Answering in FactoryClaw's terminal interface comes later.

### Decisions

A Project Manager that needs the Human records the question as a comment on the Bead it holds up, which stays claimed so `bd ready` leaves it out, and sends the question into FactoryClaw's Telegram chat with the Human with `openclaw agent --session-key "$FACTORYCLAW_SESSION" --deliver --message "…"`, naming the project, its herdr pane and the Bead; FactoryClaw's reply, rewritten for a phone, is what the Human receives, and the question stays in that chat's context for the answer. FactoryClaw relays it and types the Human's answer back into the pane, starting with `FactoryClaw:`; the Project Manager records the answer as a second comment. A Human gate inside a Run reaches the Human the same way. A fresh Project Manager session or FactoryClaw finds an open question as the last comment on a claimed Bead. The exact mechanism can change.

## Workflows

- **The Workflow library** (2026-10-19) holds every Archon Workflow on this Mac in one user-wide place, so a Workflow written while working on one project serves every project. It is the Workflow library the Profile names (`$LIBRARY` in a Project Manager's shell, at the path that Mac's Profile gives) and its own git repo, the private `github.com/bradley-mankoff/archon-workflows`, so every Workflow the person writes has history. `factory/` is the core group, the Workflows that ship with this repo in `workflows/factory/` and that `scripts/install-workflows` copies in whole on every install; a group of the person's own holds their Workflows beside it (`other/` on this Mac), and install never writes to it. Because the core group grows with the core, it opens with a router, `factory/README.md`, giving each Workflow's purpose and when to pick it, so a Project Manager reads one page and opens only the Workflow it picks; beside it, `factory/NODES.md` lists every kind of node the core Workflows use, with a snippet that passes `archon workflow test` when pasted, so writing a Workflow of one's own costs less. A core Workflow is changed, or a new one added, only for a problem every project shares, judged from the problem itself without looking at other projects, and in this repo, whose install puts it in place; a Workflow or fork particular to one project, one Mac or one private client goes in the person's own group, where installs never reach. A fork sits beside its parent in the person's own group as a sibling folder whose name starts with the parent's, with a line on how its purpose differs (`factory-build-gated` is the first, a fork of `factory-build`, and it ships in the core). The Project Manager commits and pushes a Workflow of the person's own to the library, and a change to a core Workflow to this repo, and each Run's comment on its Bead names the Workflow and the commit it ran from, so the Human can ask for a re-run with a change. Projects save no Workflows of their own in `.archon/workflows/`. The core Workflows moved from the library into this repo on 2026-11-07 (the Human, 2026-11-07; fac-qpv.6.2): `scripts/install.sh` clones the library when the folder is missing and never overwrites the person's own groups, then replaces only its `factory/` group with this repo's copy, so an install changes no Workflow outside the core group. Archon 0.12.1 shapes the layout, as tested on 2026-10-19: it finds a Workflow only at `<group>/<workflow>/<workflow>.yaml`, exactly one YAML file per folder with its `fixtures/` beside it, so a fork cannot nest inside its parent's folder; it refuses a `.git` folder there as an invalid pack, so the repo keeps its git folder beside it, `library.git` in the Archon home, and the workflows folder holds a `.git` file pointing to it; and a symlinked pack loads but `archon workflow test` finds no fixtures in it, so the files are real. The core Workflows: `factory-build` runs one ordered review pass with no loop: work, checks, a spec review that only reads, then a standards review that fixes what it finds inside the diff and commits it, the checks again, the landing (`bin/land`: the Profile's pull request, or a squash onto the base branch), and telling the Project Manager; each AI node's agent is held to the checks its `flows/` file assigns, and a work node whose agent finished with checks still failing stops the Run before the reviews, with the failed checks on the Bead (`fac-qpv.3.3`); `factory-build-gated`, the same single pass with a Human gate before the landing, whose `demo` node first records a video of the change working with the `record-demo` skill (Playwright driving the Human's Chrome, idle stretches cut by `demo/trim-idle`) for FactoryClaw to attach on Telegram, because the Human judges taste and fit without running anything (2026-10-18); a node after the gate writes the Human's reason to a `rejected` note when the Human rejects, since a reject skips the landing and `bin/land`'s `landing` and `held` notes would otherwise be the Run's last word, and `bin/finish` reads that note before them, so the Notice names the rejection and its reason rather than a landing the gate never made (fac-758); `factory-research`; and `factory-task`, one node with no review, for a Bead that asks for an answer (research, a brainstorm, a plan) or for a change it spells out exactly, which the checks gate before the landing: not every task an agent does is a change to code, and a review in the Workflow adds nothing to those (the Human, 2026-11-04). They read the project's check command from the project's uncommitted `.archon/.env` as `FACTORY_CHECK` (and `FACTORY_DEMOS` where a Workflow names it); the pane and the Bead come from the Run's message, `<pane> · <bead id>`. A Project Manager starts a Run with a message of the form `<pane> · <bead id>`, and the Workflows read the Bead from the end of it with `bin/bead`, so the web UI's input line says which Project Manager started each Run (the Human, 2026-11-04); a Mac that starts its Runs through a helper of its own does the same there. They call the Factory's helpers in `~/.local/share/factory/bin/`. Their last node runs `bin/finish` with the Workflow's name, which reads how the Run ended from the notes in its artifacts (`bin/land`'s `landing` and `held`, the gated Workflow's `rejected` with the Human's reason, pi-flows' `flows-failed.txt`, a task's `no-commits`, research's `findings.md`) and leaves the one Notice line; it never uses another node's output, such as `$land.output`, because Archon refuses to splice a failed node's output, and the first end-to-end Run's message to its Project Manager was lost that way. `bin/land` deletes a landed pull request's branch with `git push origin --delete`, never `gh pr merge --delete-branch`, which checks out the base branch and fails in a Run's worktree after the merge has happened. Their AI nodes name roles (`@work`, `@spec-review`, `@standards-review`), which Archon's `config.yaml` binds to Chain models, as "Models elsewhere" above says; the Factory's pi folder loads pi-claude-bridge as a package so a Chain can reach Claude (tested 2026-10-19). The Factory names no `xai` model: Archon 0.12.1's bundled pi provider cannot refresh an `xai` OAuth login (`Cannot find module './xai.js'`).

### What a node can control with the pi provider

Tested in two rounds on Archon 0.11.1 and rechecked in a third on Archon 0.12.1 with pi 1.3.0 (2026-10-17). The full tables and their evidence are in `reference/archon-pi-spike/RESULTS.md`. Archon's AI nodes run the pi library that Archon is built with, not the installed `pi` command; on 0.12.1 that is pi 1.3.0.

- **Works**: model and thinking level per node (`effort`; unset means pi's default; pi clamps the level to what the model offers, so set a level the model really has), system prompt (it replaces pi's opening section and keeps the project instructions), skills, allowed and denied built-in tools, retries, idle timeouts, loops with a shell exit check, groups of nodes looped together, branching on structured output, parallel nodes, pauses answered from the shell (written as `wait: {attention: …, form: approval}`; the Factory never uses the deprecated `approval:` gate), a worktree per Run that can commit and push, and shell nodes with the Run's variables (`$ARGUMENTS`, `$WORKFLOW_ID`, `$ARTIFACTS_DIR`, `$BASE_BRANCH`). A per-node `pi:` block can turn pi extensions off for that node (`pi: {enableExtensions: false}`).
- **Not supported by Archon's pi provider**, confirmed in Archon's source (`mcp:!1, hooks:!1, costControl:!1`): per-node `hooks`, per-node `mcp` and `maxBudgetUsd`. On 0.12 an `mcp:` field on a pi node stops the whole Run before it starts. Written `mcp: {path: …, optional: true}`, the Run starts but the node still gets no MCP tools, so Factory Workflows never write the field. A total `timeout` on an AI node is ignored without a warning (an 8-second limit ran 43.7 seconds). pi itself has no turn, token or cost cap.
- **Hooks instead**: pi's hooks are its extension events. An extension can block or change a tool call (`tool_call`), change a tool's result (`tool_result`), and act when a session starts, before the agent starts and on each context build (`docs/extensions.md` in pi's install). What is missing is only Archon's per-node `hooks:` field, which is written for Claude Code's hooks and is not translated for pi. A trusted project pi extension (for example `.pi/extensions/guard.ts`; tested example in `reference/archon-pi-spike/extensions/guard.ts`) blocks commands on pi's `tool_call` event, and it can act differently per node by reading a marker in that node's prompt. The extension must use the handler's `ctx`, never `pi.*` inside a handler: Archon shares loaded extensions across nodes, and the stale-context error otherwise blocks every tool call after a node's first.
- **Base branch**: a Run outside a worktree (`--no-worktree`) and a Run with `--branch` both need `worktree.baseBranch` in the project's `.archon/config.yaml` when Archon cannot work out the remote's default branch; without it, shell nodes and `--branch` Runs fail before they start.
- **Which extensions a node loads**: extensions are on or off per node, with no list of which ones. With them on, a node loads every package in the Run's pi agent directory plus every trusted extension in the project's `.pi/extensions/`. The agent directory is chosen once per Run (`PI_CODING_AGENT_DIR` when `archon` starts), not per node. So the Factory's set stays small, and an extension that should act only in some nodes checks a marker in the node's prompt and otherwise does nothing.
- **MCP**: not needed now, and nothing planned uses it. Archon 0.12.1 runs pi 1.3.0, but its pi provider still declares MCP off (`mcp: false` in `packages/providers/src/community/pi/capabilities.ts`). No Archon issue asks for it; issue #2843, which lets nodes load named MCP servers across all providers, is the nearest. pi 1.3's own MCP does not reach Archon's AI nodes either: on 2026-10-17 a node with a trusted project `.pi/mcp.json` had no MCP tools. Instead, a shell node that runs the installed pi (`pi -p … < /dev/null`, with a shell `timeout`) reaches MCP servers. Without `< /dev/null`, pi hangs.
- **Limits that work against runaway nodes**: `idle_timeout`, `retry` and loop `max_iterations`.

### A clean pi setup for Runs

By default every AI node loads the Human's personal pi setup from `~/.pi/agent`: personal extensions (their tools ignore `allowed_tools`) and personal skills. Factory Runs instead use their own pi agent directory, `~/.local/share/factory/pi-agent/`, which each Factory project names as `PI_CODING_AGENT_DIR` in its uncommitted `.archon/.env`. It holds:
- `auth.json`, a symlink to the personal one, so one OAuth login serves both and no second refresh token goes stale;
- a `settings.json` whose packages are pi-claude-bridge, pi-chains and pi-flows, and `defaultThinkingLevel: "high"`;
- `chains.json`, a link to the Chains file the Profile names, where pi-chains looks for the roles, so every Run node runs on its Chain (fac-qpv.8.1);
- a `trust.json` trusting the folder where Archon puts Run worktrees, and each Factory project's repo in case a Run opens it directly;
- `agents/`, the agent definitions the `subagent` extension reads; install links `scout.md` into `~/.pi/agent/agents/`, so the Human's own sessions and Project Managers have it too.

Project Managers do not use this folder: they start the Human's own pi, so their sessions are kept with his other pi sessions (the Human, 2026-11-07). This folder is for Runs.

No `models.json`: pi 1.3's built-in catalog has every model the Factory names. `auth.json` holds credentials, so the live directory sits outside this repo; `pi-agent/` here keeps the other files and the setup steps. Tested result: built-in tools only, no personal skills, and node sessions written to that directory instead of `~/.pi/agent/sessions`.

Accepted as they are:
- Archon's pi nodes always load `AGENTS.md` files from the agent directory and from every parent folder, so `~/AGENTS.md` and `~/Developer/AGENTS.md` reach every node of a repo under the home folder.
- There is no cost or token cap.
- On Archon 0.11.1 a hidden call titled each Run, with its model from the `TITLE_GENERATION_MODEL` environment variable and its thinking level from the agent directory's settings. On 0.12.1 none of the 51 node sessions in the third round was a title call, nor any of the 7 sessions of the first two calculator Runs (2026-10-18).

### Sessions

Every node writes an ordinary pi session, into the Factory's own agent directory under the clean setup. The Factory decides which of those sessions reach memory, so Runs do not flood the memory bank.

## Memory

| Who | Remembers | Where |
|---|---|---|
| PersonalClaw (outside the Factory) | Everything machine-wide; of the Factory, only how to think about it and talk to it | OpenClaw memory in its workspace, with cross-conversation recall in direct chats |
| FactoryClaw | The Human's communication style; how the Factory works and how it is changing; the basics of each project | OpenClaw memory in its workspace; no cross-conversation recall, since it mostly relays |
| Project Manager | The whole lifecycle of its project; which tools and Workflows worked there | Beads only: the project's issues and comments, and `bd remember` lessons that `pi-beads` loads |
| Scouts and AI nodes | Nothing beyond their task or Run; they write no memory | — |

Decided by the Human on 2026-10-22 (`fac-60v.20.7`), after a lesson on OpenClaw's memory (`docs.openclaw.ai/concepts/memory` and `memory-architecture`):
- **Each kind of agent keeps its own memory.** Project Managers do not use OpenClaw's memory, neither its memories nor its engine: OpenClaw captures and recalls only inside its own sessions, and Beads already holds each project's decisions and travels with the repo. OpenClaw likewise keeps sub-agent, cron and heartbeat sessions from writing memory, which is why Scouts and nodes write none.
- **A Project Manager's gaps are closed in Beads:** the pi-beads package saves a session's lasting lessons with `bd remember` at session end and before compaction (`fac-60v.20.19`), and a consolidation run merges, supersedes and prunes a repo's `bd memories` (`fac-60v.20.20`).
- **The Factory's own memory is this repo's Beads.** A Project Manager that meets a problem with the Factory searches them with `bd -C ~/Developer/personal_code/factory` and files a Bead there when the problem is new, as the `workshop-catch` plugin does (`fac-60v.20.17`).
- **A Scout reads** the sending Project Manager's memory (`bd memories`, `bd search`) when the task needs it, and never OpenClaw's memory.
- **The Claws' dreaming promotes nothing yet:** promotion needs a note recalled 3 times by 3 different searches, and the Claws rarely search their memory, so no candidate qualifies (`fac-60v.20.18`). Active Memory (on for PersonalClaw and WorkClaw) and instructions to search memory supply those signals; curated `MEMORY.md` files written with the Human are the reliable path. Each Claw gets its full set of memory files (`USER.md`, `MEMORY.md`), written with the Human.

Every Run leaves a comment on its Bead naming its Workflow and the commit it ran from, and a landing: a pull request on the personal Mac, or the squash onto the Project Manager's branch on the work Mac.
